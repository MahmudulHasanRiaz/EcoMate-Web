## 0. Changes incorporated from the 6 architectural corrections

1. **No customer merge/split operations in Wave-2.1.** Wave-2.1 only makes the identity model **future-compatible**: a stable, nullable, unique `CustomerProfile.externalId` + a centralized resolution component that a future merge/split can reuse. No `mergeCustomers` op, no admin UI.
2. **No rewrite of existing TrackingContext rows.** Chosen design is **identity-binding** (resolve `external_id` authoritatively per order at dispatch, and bind NEW contexts at create), justified against the rewrite alternative in §2.2.
3. **`/auth/me` and Pixel external_id are verified, not assumed** (§4), against the existing storefront auth flow and Meta guidance (fbq init Advanced-Matching `external_id` param) before any code.
4. **Centralized Identity Resolution Service** — single authoritative component resolving `external_id` for every channel (Web, Admin, POS, Public API, Mobile) via the shared capture→dispatcher path (§3).
5. **Tenant isolation + license-gated deployment** verified and designed (§5).
6. **Lifecycle analysis extended**: customer deletion, re-registration, cross-channel identity continuity (§6).

## 1. Objective (unchanged)
Stable customer-keyed `external_id`, propagated to CAPI + Pixel, guest lifecycle intact, backward-compatible, flag-gated. No payload hygiene / browser event_id / dedup-window / consent / AM / context-refresh work in this wave.

## 2. Identity model & resolution

### 2.1 Model
- `CustomerProfile.externalId String? @unique` (nullable; lazily assigned; opaque UUID).
- `TrackingContext.externalId` unchanged (journey uuid default) — **new** context rows created for an authenticated user are **bound at create** to the customer `externalId`.

### 2.2 Binding vs rewrite — justification (mandated)
| | Rewrite existing context rows | **Identity-binding (chosen)** |
|---|---|---|
| Replay consistency | **broken** — a replayed event for a rewritten ctx would carry a *different* external_id than its original dispatch → Meta dedup path (b) inconsistent | **preserved** — resolve per order/customer at dispatch; replay reuses the same customer key |
| PII rewrite risk | rewrites PII-bearing rows (non-reversible, expensive) | none (no historical write) |
| Historical attribution | at risk | untouched |
| Reversibility | poor | full (flag off) |
| Deletion coverage | all contexts reachable | post-claim (bound-at-create) contexts reachable; abandoned pre-auth contexts remain out of reach (inherent, not worsened) |

**Decision:** identity-binding — resolve `external_id` at dispatch via `order.customerId → CustomerProfile.externalId` (when the flag is ON), else fall back to the context journey uuid; bind NEW contexts at create. No rewriting of existing rows.

## 3. Centralized Identity Resolution Service
New backend service `IdentityResolutionService` (single authoritative component):
- `ensureForCustomer(customerId, tx)` → lazily assign `CustomerProfile.externalId` (uuid) inside a `$transaction`.
- `resolveForOrder(order, ctx)` → `external_id` = customer binding (flag ON) else `ctx.externalId`.
- Injected into `TrackingDispatcherService` (which is the single funnel for **Web / Admin / POS / Public API / Mobile** — all channels capture through `TrackingCaptureService` → dispatcher, so one resolver covers every channel). Future channels call the same component.

## 4. Verification performed before code (correction 3)
- **`/auth/me`:** verified in `auth/auth.controller.ts:120` (`@Get('me')`). Payload confirmed to include the authenticated user + `CustomerProfile` linkage (via `betterAuthUserId`); an `externalId` field will be appended **only when the feature flag is ON** (additive, no shape change when off).
- **Pixel external_id:** Meta guidance (Advanced Matching / init params) — `fbq('init', pixelId, { external_id })` is the documented way to pass a raw `external_id`; Meta hashes it (lowercase + SHA-256) identically to our CAPI `hashExternalId`, so the same raw value matches. **Re-init:** the Pixel does not support true re-init after load, so the storefront will call `fbq('init', metaId, { external_id })` **once, with the value known at mount** (user from the client auth store; `setPixelIdentity` buffers until both ids + user are available, then initializes with the param). For guests the init stays parameterless (unchanged). **No assumption of re-initialization.**

## 5. Tenant isolation + license gating (correction 5)
- `external_id` is a global UUID → no cross-tenant collision (unique globally). Single-store deployments unaffected.
- Gating: `tracking_customer_external_id` (settings/env `TRACKING_CUSTOMER_EXTERNAL_ID`, **default OFF**) AND the existing tracking feature/license grant (same model as `tracking_relay_enabled` / `admin_tracking`) — resolution only activates when BOTH the settings flag is ON and the tenant holds the tracking feature. Verified the license feature key set (`packages/shared-types/src/license-types.ts`) includes the tracking grant; the plan reuses it (no new license key).

## 6. Lifecycle (extended)
- **Guest (anonymous / checkout):** journey uuid; em/ph at checkout; unchanged.
- **Guest → authenticated (register/login):** `ensureForCustomer`; NEW contexts bind to the customer key (created after the claim); no historical rewrite.
- **Deletion:** `deleteByCustomerId` deletes contexts by customer key (post-claim) + orders→ctx (existing path); abandoned pre-auth contexts remain out of reach (documented limitation, not worsened).
- **Re-registration:** a deleted customer re-registers → new `CustomerProfile` → new external_id → fresh identity (old contexts were deleted); no key reuse.
- **Cross-channel continuity:** POS / Admin / Public API / Mobile orders for the same authenticated customer resolve the same `external_id` via `IdentityResolutionService` → consistent identity across channels.
- **Merge/split (future):** not implemented; the model (opaque mutable `externalId` + central resolver) is designed so a future merge re-points `CustomerProfile.externalId` only, and all channels follow via the resolver.

## 8. Backward compatibility
- Flag OFF → byte-identical behavior (journey uuid; no Pixel external_id; no schema reads).
- Guests unchanged. Event shape/event_id/hashing/dedup unchanged.
- Schema additive + nullable; migration hand-authored (additive column), no data rewrite.

## 9. Migration
1. Add column via migration (`customer_external_id`, nullable unique) — hand-authored per AGENTS.md (no DB in sandbox), committed with schema.
2. Lazy assignment (no backfill of profiles/contexts).

## 10. Risks
- Identity behavior change mid-rollout → default OFF; enable per-server.
- `ensureForCustomer` race → `$transaction` + unique constraint (retry on P2002).
- Pixel init ordering (user loads async) → `setPixelIdentity` buffers until both ids + user present; no re-init.
- Replay consistency → identity-binding resolves per order (safe).
- Deletion limitation documented (not worsened).

## 11. Out of scope
Merge/split ops, journey-stable browser event_id, mirror idempotency, 48h guard, consent/opt_out, AM beyond `external_id` init param, context refresh, zp/st/ln, num_items, Dataset Quality reader.
