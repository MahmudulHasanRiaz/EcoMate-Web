# ADR — Wave-2.1 Identity Architecture Final Decisions

**Status:** Accepted (final architectural cleanup before commit).
**Date:** 2026-08-04
**Scope:** six review items raised on the Wave-2.1 implementation. One adjustment made (item 2); the rest are keep-with-evidence.

---

## ADR-1 — Where the identity resolver + endpoint live (items 1 & 4)
**Decision: KEEP `IdentityResolutionService` and `GET /tracking/identity` in the Tracking module.**
- `IdentityResolutionService` is the **tracking match-key resolver**: it reads `CustomerProfile` only to produce the tracking `external_id`, it is flag-gated by a tracking setting (`tracking_customer_external_id`), and its only consumers are the dispatcher and the identity endpoint. It is not a general customer, auth, or tenant concern.
- The customers module is admin-gated (`@Roles('superadmin','admin','manager')` + `admin_customers`), so a shopper endpoint cannot live there without auth restructuring; the auth module owns credentials/sessions, not match keys; a shared identity domain has zero current consumers (YAGNI). A future enterprise identity graph (audit candidate H) is a deliberate later wave and can re-home the service then.
- **Evidence:** customers.controller admin gating; auth.service.me returns the admin UserProfile; single-consumer graph.

## ADR-2 — Meta Pixel external_id lifecycle (item 2) — ADJUSTMENT
**Decision: data-driven init with buffered Meta events.**
- Meta supports `external_id` only as an `fbq('init')` Advanced-Matching parameter; there is **no reliable post-init setter** (no re-init), and the fbq stub processes queued calls in order, so `init` must precede any `track`.
- Implemented: `initMetaPixel()` (idempotent, runs `fbq('init', id, {external_id})` + PageView), Meta events **buffer in `_eventQueue` until init** (init-first ordering), and TrackingScripts **arms init readiness only after pixel id + identity are both known** (guests resolve immediately to null).
- Result: for an authenticated shopper the `external_id` is **present at init** — no dependency on a future page load; guests are parameterless (unchanged).
- **Trade-off:** the very first PageView for an authenticated shopper is delayed until the identity fetch resolves (a same-origin call); the pixel tag still loads async and events are buffered. **Evidence:** Meta AM init-parameter guidance; fbq stub queue ordering; code `tracking.ts` `initMetaPixel`/`_metaInited`, `TrackingScripts.tsx` readiness effect.

## ADR-3 — snapshot `customerId` contract (item 3)
**Decision: KEEP the optional, additive contract.**
- `TrackingSnapshotPayload.customerId?: string` is optional and additive. Order-bound events (Purchase/Refund/offline) set it at capture; browser-origin events and leads omit it by design (no server-side customer binding at those points). Any future event type with a customer can set the field without a schema change; resolution stays centralized in `IdentityResolutionService` (per-order, flag-gated). **Evidence:** `tracking-snapshot.types.ts`; orders/checkout-leads capture payloads; no other event type needs it today.

## ADR-4 — concurrency & feature/license disable (item 5)
**Decision: KEEP (verified safe).**
- **Concurrency:** `ensureForCustomer` is P2002-safe (unique constraint; a concurrent assign is re-read) — covered by `identity-resolution.service.spec`. Concurrent dispatches for the same customer converge to one uuid.
- **Flag disable:** identity-binding writes nothing, so disabling `tracking_customer_external_id` simply stops resolution → fallback to the journey uuid. No data corruption; a dispatch that read the flag while ON may still send the customer key across the transition boundary (acceptable, same as any flag toggle). Deleted customers resolve to null → journey uuid (no crash).
- **License:** the resolution flag is a settings gate (same model as `tracking_relay_enabled`); the admin tracking surface (monitoring/replay/deletion) is additionally license-gated via `admin_tracking`. A stricter license gate on identity resolution is a one-line addition if the architect requires it — not needed today. **Evidence:** `isEnabledOrDefault`; `identity-resolution.service.spec`; dispatcher fallback tests.

## ADR-5 — Overall
Only ADR-2 changed behavior. ADR-1, 3, 4 keep the implementation. Rationale documented above; no further architecture work in Wave-2.1.
